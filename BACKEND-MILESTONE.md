# Dearelle V2 commerce backend

This milestone runs locally with public intake OFF. The schema only permits synthetic `test` orders; changing an environment flag cannot enable live commerce. No hosted database, owner account, staging deployment or production migration is provisioned by these scripts.

## Architecture and security

Next.js uses a private `commerce` PostgreSQL schema through the `dearelle_app` role. Supabase's Data API does not expose it. All tables have RLS; anonymous and authenticated roles have no schema/table/function access. The runtime role cannot grant owners or change business settings. It has no Supabase service key. Amounts are integer paise in normalized tables; immutable quote and line snapshots preserve the rupee-based UI contract. The existing SQLite class is retained only for regression tests, with no application routes using it.

Orders, lines, idempotency and reservations commit together. Inventory constraints and triggers reject overselling. Checkout locks inventory in SKU order; duplicate requests take a transaction advisory lock, replay the same order and reject changed payloads. Reservations transition once to released or consumed, with append-only inventory auditing. Dispatch consumes physical stock; cancellation before dispatch releases only the reservation. Historical line/payment/audit records cannot be updated or deleted by the runtime role.

Expiry proposes **24 hours**, configurable in `commerce.settings` for test orders. A local worker (`scripts/expire-reservations.mts`) releases only expired, unfunded awaiting-contact/confirmed orders. Verification and expiry lock the same order row. Verified orders never expire. No hosted scheduler is created. Live expiry needs owner approval and a separately reviewed schema change. For hosted scheduling, use a private scheduled job with scoped credentials, not a public unauthenticated endpoint.

Supabase Auth email/password-only sign-in is mediated by server routes; sign-in TOTP enrollment/challenge API actions and UI have been removed at the owner’s request. Existing registered TOTP factors and recovery checks remain unchanged. Auth cookies use the distinct `dearelle-owner-auth` name to avoid collisions with other projects on localhost. Auth cookies are HttpOnly, SameSite Strict and Secure on HTTPS. No auth tokens are returned in JSON or stored in browser localStorage. Each sensitive request verifies the user, the server-managed single-owner allowlist, verified password AMR and subject binding, the actual Auth session, and an unrevoked owner session (30 minute idle / 8 hour absolute). Logout revokes local authorization before invalidating the Supabase session. The narrow auth-session lookup is the sole security-definer function, with fixed empty search_path and access granted only to the runtime role. Public Auth signup is disabled in local config; enforce the same hosted setting before staging.

Request bodies are same-origin JSON, streamed with a 16 KiB cap. Server-computed quotes use database prices/availability. UUID references and a random HttpOnly guest cookie protect private confirmations; only its SHA256 digest is persisted. Durable HMAC-keyed rate buckets hold no raw IPs. Staging's trusted proxy must overwrite forwarding headers. Use a WAF/IP limiter in addition to these application limits before public launch. No customer/order data belongs in logs or analytics.

## Local setup

Use the pinned CLI and dependencies (`pnpm install --frozen-lockfile`). Docker Desktop is required. Run `pnpm exec supabase start` with this project's config (ports 55421/55422/55423); wait until startup finishes before running setup. The CLI applies the versioned migration and seed. `pnpm exec tsx scripts/setup-local-commerce.mts` creates a random limited-role password and stores local runtime configuration in ignored `.env.local`. It refuses non-loopback bootstrap URLs. It never resets existing inventory.

Save `pnpm exec supabase status -o env` into ignored `.data/supabase-status.env`; do not paste keys in chat or commit them. Local owner fixtures are created by `scripts/setup-local-owner.mts`, only against 127.0.0.1. For a real owner, use a separately authorized invitation/bootstrap, disable public registration and remove all synthetic accounts. Current application sign-in requires email/password; it no longer enrolls or challenges TOTP during sign-in. Owner allowlisting is an administrative SQL operation, never controlled by user metadata.

Test commands: `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`; `pnpm exec tsx scripts/test-postgres.mts` and `pnpm exec tsx scripts/verify-commerce.mts` require the isolated local database and test server. Database tests use synthetic customers and exercise real concurrent connections. They must never target a hosted or production database.

## Manual COD workflow

Customer contact confirmation → manually check external ₹50 advance → record exact amount/reference/internal note → pack → enter tracking and dispatch → deliver → record exact remaining COD and settlement reference. ₹50 is per order, deducted from total; shipping is free across India. Nothing here collects payment or automatically marks an advance received. References are unique and records include owner identity and database timestamp. A funded cancellation remains visible with its payment record; refund handling must be agreed before live launch.

## Backup, recovery and retention

Before staging approval: choose Supabase Mumbai ap-south-1, an isolated V2 project with deployment protection, appropriate backup/PITR plan and a separate staging environment. Confirm pricing before provisioning. Never link this repository to dearelle.in. Store the runtime connection URL and publishable key only in server-side staging secrets, use TLS with certificate validation (the managed pooler URL), disable public registration, invite one owner, configure exact origin and HTTPS Secure cookies. Review grants/RLS and migration against an empty staging database before applying approved migrations. Keep PUBLIC_ORDER_INTAKE=0 and test-only schema constraints.

Backups must include schema, immutable financial/audit tables and stock, plus separate Auth configuration/user recovery planning. Use encrypted off-site backups, restricted access, a documented retention period and regular restore drills into an isolated database. Never restore over a running live database. Local drill: `pg_dump -Fc` via the project's database container, create a separate recovery database, restore with `pg_restore` under the local Supabase administrative database role (`supabase_admin`; restoring internal Supabase functions as the restricted `postgres` role can fail), compare inventory/order/payment counts and checksums, run constraints/security checks, then drop only that named scratch database after review. Record actual RPO/RTO from hosted restore exercises; neither is guaranteed by local tests. Supabase Auth owner recovery/MFA loss needs a documented, identity-verified administrative process and owner-controlled recovery access. Existing registered factors and recovery checks remain unchanged; the password-only application sign-in change does not remove recovery MFA.

Retention is deliberately unapproved/unset. The schema-owner-only `commerce.anonymize_closed_orders()` function refuses to run until a retention period is explicitly approved. It removes customer contact data and guest access from old unfunded cancelled/expired orders and fully reconciled delivered orders, preserving financial lines/payment records and appending an audit. Paid cancellations are excluded while refund handling is unresolved. It is not callable by the runtime or Data API, and has no automatic schedule. No destructive cleanup of customer or financial records runs automatically. Before live use, approve lawful retention periods, accounting requirements, privacy notice, deletion/anonymization procedures, backup expiry and support access. Rate buckets can be pruned after one day by an approved maintenance job; they contain only HMAC keys and counters. Guest access expires after 24h, separately from database retention. Owner PII is visible only within authenticated management screens. Any future anonymization must retain financial snapshots and audit evidence without preserving unnecessary customer identifiers.
